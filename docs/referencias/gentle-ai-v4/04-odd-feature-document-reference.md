# ODD Feature Document Reference

## Purpose

This document explains the relationship between:

1. the external **ODD Execution Brief** generated by the custom GPT; and
2. the runtime **ODD feature document** that Pi may create for substantial implementation.

They are not the same artifact and do not have the same owner.

---

## 1. Ownership

### ODD Execution Brief

Owner:

- user + briefing GPT.

Purpose:

- transfer intent;
- define scope;
- preserve product decisions;
- define acceptance;
- preserve constraints;
- define evidence expectations;
- define Git/delivery authorization;
- define human stop conditions.

Created:

- before handing work to Pi.

It should be understandable without hidden memory.

### Runtime ODD feature document

Owner:

- Pi / Gentle Shell runtime during implementation.

Typical path:

`odd/tasks/<feature-name>.md`

Purpose:

- recoverable operational implementation state.

Created:

- after Pi explores/classifies the work as substantial;
- before source changes when durable tracking is needed.

The external GPT does not create or claim this runtime artifact by default.

---

## 2. Key distinction

ODD Execution Brief
≠
`odd/tasks/<feature-name>.md`

The briefing answers:

- What do we want?
- Why?
- What is authorized?
- What must remain true?
- How will humans recognize success?
- What delivery actions are allowed?

The feature document answers:

- What repository-grounded work units exist now?
- What task is current?
- What has actually been completed?
- What evidence exists?
- What remains?
- What changed in the plan because of observed reality?

---

## 3. When a feature document is appropriate

Small, understood work does not need durable feature tracking.

Substantial work does.

Substantial means:

- coordinated meaningful implementation steps; or
- progress worth recovering across interruptions/sessions.

It is not defined by a fixed line threshold.

The decision belongs to Pi after repository exploration.

---

## 4. Recommended feature document content

A runtime feature document may contain:

# <Feature / HU Name>

## Objective

Current accepted objective.

## Problem / Why

Why the implementation matters.

## Authorized Scope

Current authorized implementation boundary.

## Constraints

Technical/product constraints still applicable.

## Acceptance Criteria

Current observable completion criteria.

## Tasks

Example conceptual shape:

- [ ] `T01` Repository-grounded work unit
- [ ] `T02` Next work unit
- [ ] `T03` Verification/documentation work unit

Task IDs should remain stable enough for recovery.

## Current Task

Which task is active.

## Progress

What is actually done.

## Evidence

Observed checks/results tied to work.

## Blockers

Current genuine blockers.

## Next Action

Exact next unfinished action.

## Relevant Rationale

Concise rationale for meaningful accepted changes to the implementation plan.

This is a living ledger, not a second product specification system.

---

## 5. What NOT to put in the feature document

Avoid:

- a duplicate SRS;
- a duplicate HU catalog;
- an exhaustive chronological journal;
- speculative repository design before exploration;
- hidden scope expansion;
- invented PASS results;
- unrelated project backlog;
- secrets;
- raw credentials;
- massive unbounded logs.

Permanent project truth belongs in the project's permanent documentation.

---

## 6. Engram mirror

For substantial work, Pi may mirror the **full current feature document** to project-scoped Engram topic:

`odd/<feature-name>/tasks`

The mirror helps recovery.

It is not a replacement for the actual repository file.

The external briefing GPT must not claim the mirror exists or is current.

---

## 7. Correct write/recovery behavior

When Pi owns substantial work:

1. maintain local feature progress;
2. mirror it to Engram when available;
3. read back/confirm both when required by runtime;
4. keep progress truthful;
5. mark mirror pending when unavailable rather than claiming success.

On resume:

1. read current user requirements/decisions;
2. read the actual feature document;
3. recover the full project/feature-scoped memory when available;
4. inspect current repository state;
5. reconcile evidence;
6. continue the next unfinished valid work unit.

Do not infer the active feature only from the newest global memory.

---

## 8. Conflict handling

If feature file and memory disagree:

- do not silently prefer the newer timestamp;
- preserve surviving progress;
- compare against repository evidence;
- compare against latest user decisions;
- resolve deterministic differences;
- ask only if a genuine product/risk decision remains.

If one copy is missing:

- preserve the surviving copy;
- do not overwrite it based on absence;
- restore/mirror only after reconciliation.

---

## 9. Requirement changes

When the user changes an accepted decision:

- update affected intent;
- modify affected pending tasks;
- preserve unaffected completed tasks;
- reopen invalidated completed work with a reason;
- update checks/evidence expectations;
- add genuinely new work only when authorized.

Do not recreate the whole feature unnecessarily.

---

## 10. Task completion and evidence

A task should be marked complete only when its intended outcome is observed sufficiently.

Possible evidence:

- test result;
- build/typecheck/lint result;
- runtime/manual behavior;
- API result;
- data-state verification;
- visual evidence;
- documentation update;
- commit when explicitly authorized.

Unavailable or failed checks must be recorded honestly.

A checkbox never manufactures evidence.

---

## 11. Session/UI task projection

The runtime may project substantial feature tasks into its session todo UI.

That projection is not a third source of truth.

The durable file and memory mirror remain recovery artifacts; UI/task projection should reflect them rather than replace them.

If the UI projection is unavailable, do not pretend it synchronized.

---

## 12. Permanent documentation boundary

Operational tracking is not permanent project documentation.

Example separation:

`docs/historias/`
→ functional HU truth

`docs/requirements/`
→ cross-cutting requirements

`docs/architecture/`
→ durable architecture

`docs/adr/`
→ architectural decisions

`docs/evidence/`
→ delivery evidence

`odd/tasks/`
→ current recoverable implementation state

When implementation changes durable truth, Pi should update the permanent docs as part of the work.

---

## 13. Git/work-unit relationship

Work-unit commits may be useful when local commits are explicitly authorized.

For Pi / Gentle Shell, do not assume commit permission.

The briefing's Git/Delivery Authorization controls what Pi may do.

Commit permission never implies:

- push;
- PR creation;
- merge;
- deployment.

The feature document may record work-unit/delivery progress when the runtime uses those boundaries.

---

## 14. Reviewability heuristic

A rough ~400 authored changed-line budget may help review/delivery slicing.

It is advisory.

It is not:

- a hard task size;
- a reason to split coherent atomic behavior incorrectly;
- a reason to drop tests/docs;
- a reason to compress code;
- a product acceptance criterion.

Pi should choose work-unit boundaries based on repository reality and safe reviewability.

---

## 15. Review boundary

Native review configuration is separate from feature tracking.

The feature document may record review evidence/outcome when the runtime produces it, but it does not control review mode.

Review does not authorize remote delivery.

---

## 16. External GPT rule

The briefing GPT may say:

`If repository exploration classifies this implementation as substantial, create and maintain one recoverable ODD feature document and its project-scoped memory mirror when available.`

It must not:

- pre-create repository-derived tasks as facts;
- assert the feature file already exists;
- assert memory is synchronized;
- substitute the feature ledger for HU/SRS/requirements documentation.
